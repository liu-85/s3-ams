# A1 通道进料成功 —— 完整总结

**日期**：2026-10-25
**固件**：v1.1.12（`1.1.12-s3ams`）
**通道**：A1（AMS 0 / 通道 0 / 料位 0，离合掩码 `0x01`）
**结果**：**进料全流程通过** —— 送料 → 挤出机咬住 → 跟随送料 → 进入使用态，全程无「挤出失败」弹窗，无中途退料。

---

## 一、一句话结论

不是协议不对，也不是消息给早了。是**我方状态机被打印机自己的周期性查询反复抹掉**，
导致（1）电机断续启停、耗材时松时紧 → 挤出机拉一点就拉不动；
（2）`now_filament_num` 被清成 `0xFF` → 退料请求全被拒 → 有时退料电机不动。
再加上**单电机 + 离合的机械结构**决定了打印时必须主动跟随送料，而原逻辑是停死的。

四处修复叠加起来，A1 才通。

## 四、三次误判（记录下来，避免重犯）

### 误判 1：以为是计米单位错

确实发现计米放大 1000 倍（`dt` 毫秒当秒用），送料 3.3 秒报 **141 米**、第二次 **818 米**。
这是真 bug，也真的会让打印机提前判"早已到位"——但修完（v1.1.11）**现象没变**。

> 教训：找到一个 bug ≠ 找到根因。它只是叠加因素之一。

### 误判 2：以为是"485 消息给早了 / 给错了"

把 Tianshu 的 `process_motion_state_machine` / `send_for_Dxx` / `get_pressure_value`
逐行对比，**完全一致**（唯一差异是我们多加了 `now_filament_num < 16` 越界保护）。

> 教训：移植代码没问题时，去看**输入**——打印机的帧本身可能和我们假设的不一样。

### 误判 3：以为"断开当前通道离合"能解决

用户提出这个方案，听起来合理。但日志证明：`09/A5`（准备使用）期间本来就是
`离合=0x00`、`电机=停止`、`电流=0mA`，耗材照样拉不动。

**因为离合只断开"电机↔主动轮"，压轮始终压着耗材**，阻力来自齿轮组反向拖动。

> 教训：机械结构决定软件策略。断离合不是"松开耗材"。

## 五、四个真实根因

### 根因 1：`0x0F` 被当成"清空全部通道"（最关键）

**证据**（同一时刻，前后两行）：

```
[15:06:10] RX type=04 ams=00 statu=0F motion=00 read=FF   ← 打印机"使用中"的查询
[15:06:10] TX len=60        use=0x00 pressure=0xFFFF 料位=FF   ← 我方应答：状态全没了
```

`send_for_Dxx()` 里 `read_num == 0xFF` 分支**无条件**清空 4 个通道 + `now_filament_num = 0xFF`。
而打印机在"使用中"会周期性发 `statu=0x0F + read=0xFF`（这份日志 33 帧）。

后果①：状态在"送料"和"全清"之间反复横跳 → **电机断续启停 → 耗材时松时紧 → 挤出机拉一点就拉不动**。

后果②：`now_filament_num = 0xFF` 之后：

```cpp
get_loaded_filament() → 0xFF          // 因为 now 不在 [ams*4, ams*4+4) 区间
allow_stop = (0xFF == 通道) → false   // 恒 false
→ 09/3F (before_pull_back) 和 03/00/FF (pull_back) 全被拒 → 退料电机不动
```

**这就是「有的时候退料没动作」的真正原因。**

**修复**：只有 `statu_flags == 0x00`（明确的复位/取消）才允许清空，其余一律保留。

### 根因 2：`0x0F` 是"使用中"，我们只认 `0x07`

整份日志的统计：

| 帧 | 次数 |
|---|---|
| `0x0F/0xFF` | 123 |
| `0x0F/0x00` | 33 |
| `0x07/0x7F` | **0** |
| `0x07/0x00` | 3 |
| `0x01`（停止广播） | 1259 |

`0x0F = 0x01|0x02|0x04|0x08`，比 `0x07` 多的那个 **bit3(0x08) 就是"正在使用"**。

只认 `0x07` 的后果：`on_use` / `stop_on_use` 永远匹配不上，状态卡在 `before_on_use`。

**修复**：`0x07` 与 `0x0F` 都接受；同时给 `statu=0x01` 停止广播加保护——**打印中的通道不许被清成 idle**。

### 根因 3：`read=0xFF` 时固定回 `pressure=0xFFFF`（无耗材）

打印机在 `0x0F`（使用中）阶段周期性查询当前料位，我方回"无耗材" → 打印机认为 AMS 掉线/空料。

**修复**：`read=0xFF` 且 `statu` 为 `0x03/0x0F` 时，用**当前料位**的状态回答；只有 `statu=0x01` 才回 `0xFFFF`。

### 根因 4：`before_on_use` 时电机停死（用户要求的功能）

Bambu 官方 wiki 对缓冲器的说明：

> By controlling the feed speed of the AMS, we can make sure the tension on the filament
> is within a given range so that the toolhead extruder can work easily and precisely,
> without adding too much or too little tension.

→ 打印时 AMS **必须主动控制送料速度**，不是停着不动。

但 Tianshu 是 **4 个独立电机**，打印时电机不通电 = 耗材完全自由，所以它不需要这段。
本工程是**单电机 + 离合**，停料 = 耗材被齿轮组拽住 → 必须跟随。

**修复**：`before_on_use` 期间脉冲送料：

```cpp
#define FOLLOW_FEED_ON_MS   250    // 送 250ms
#define FOLLOW_FEED_OFF_MS  350    // 停 350ms
// 100% PWM ≈ 50mm/s → 平均 50 × 250/600 ≈ 21mm/s
// 略高于挤出机拉料速度（10~20mm/s），保证不绷紧；
// 停的 350ms 让缓冲器吸收多送的料，不顶进喷嘴。
```

> **为什么不用微动驱动这一段**：微动是 ADC 三态分压，现场信号不稳（悬空 371mV
> 就落在 START 区），而 `before_on_use` 只持续几秒，等微动触发太慢。

## 六、附带修掉的三个坑

| # | 坑 | 后果 |
|---|---|---|
| 1 | `check_buffer_status()` 在退料期间仍在跑 | 缓冲满时 `AMCU_buffer_assist_feed()` 调 `AMCU_drive_stop()`，内部 `clutch_request_release_all()` **覆盖掉挂起的退料吸合请求**（`s_pending_clutch` 只有一个槽）→ 退料请求永远等不到吸合 |
| 2 | `before_on_use` 通道没从缓冲逻辑里让出 | 跟随泵和微动逻辑交替驱动同一台电机 → 现场"抖一下、抖一下" |
| 3 | 跟随泵退出时若停在"送"相位没主动停 | 交回 `on_use` 时微动若在 MID，电机会一直转着把料顶进喷嘴 |

对应修复：退料优先级最高（整段跳过缓冲逻辑）、`before_on_use` 通道 `continue`、退出时按需停电机。

## 七、这次成功的关键：能看清状态机了

修 bug 的前提是**看得见**。这次同步重写了 PC 端抓包脚本（`tools/mon485.bat`）：

| | 旧 | 新 |
|---|---|---|
| 丢帧率 | **13%**（3 分钟丢 1867 条） | **0.7%**（27 秒丢 18 条） |
| 日志 | 只在控制台，滚掉就没了 | 同时写 `tools/logs/*.log` |
| 丢帧可见性 | 不知道丢没丢 | 每帧带 `#seq`，断了红字告警 |
| 电机动作 | 埋在状态行里 | 独立黄色 `★电机` 事件行 |
| 帧解码 | Cxx/Dxx 混着解 | 只解 `type=0x04` |

**丢帧从 13% 降到 0.7% 是这次能定位 `0x0F` 的直接原因**——旧脚本每轮除了拉帧还要打
`/log` 和 `/status`（各 20~40ms 往返）+ 100ms 休眠，空档超过 400ms，
而设备端环形缓冲只够 400ms，关键那几帧正好被顶掉。

> 固件端一行没改。全部在 PC 端用"抓帧优先 + 内层追平 + 降频慢通道"解决。

## 八、成功的时序长什么样

```
打印机                          AMS
  │  Dxx 03/00 read=01            │  内部 → send_out
  ├──────────────────────────────>│  吸合离合 0x01，电机正转 100%
  │  Dxx 09/A5 read=01            │  内部 → before_on_use
  ├──────────────────────────────>│  ★ 跟随泵 送250/停350ms，平均≈21mm/s
  │  Dxx 0F/FF read=01            │  内部 → on_use
  ├──────────────────────────────>│  交给缓冲微动按需补料
  │  (周期性 0x0F/00、0x01)        │  ★ 状态不再被抹掉
  │<──────────────────────────────┤
```

`/status` 的 `feed` 段应该看到：

| 字段 | 期望 | 实测 |
|---|---|---|
| `phase` | 依次 `before_on_use` → `on_use`，不卡在 `none` | ✅ |
| `follow` | `before_on_use` 期间在 `1/0` 间跳 | ✅ |
| `meters` | 送料 1 秒约 +0.05 米 | ✅ |
| `clutch_mask` | 送料期间 `0x01` | ✅ |

## 十、方法论沉淀

这次绕了三次弯，可复用的经验：

1. **先确认"输入对不对"，再怀疑"处理逻辑"** —— 移植代码逐行一致时，去看打印机的帧
2. **抓包工具的可信度决定排查效率** —— 13% 丢帧的日志会把人带进沟里；
   在改业务逻辑之前，先把观测手段修好
3. **同一个 bug 可能解释多个现象** —— `0x0F` 误清空同时解释了"挤出失败"和"退料不动"，
   当一个修复能同时解释两个症状时，方向大概率对了
4. **机械结构决定软件策略** —— 断离合 ≠ 松开耗材；4 电机方案的经验不能直接套到单电机
5. **记录误判** —— 计米那个 bug 是真的，但修完没效果，这个事实本身就是线索
