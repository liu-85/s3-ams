# v1.1.25 —— 485 链路诊断 + 缓冲送料超时兜底

> 版本：`1.1.25-s3ams`
> 日期：2026-10-31
> 主题：**把 `[0500-40A3] AMS A 通信异常` 定性**，顺带给缓冲送料加安全上限

---

## 一、这一版做了什么

### 1. 新增 485 链路诊断计数（核心）

`/status` 的 `ams` 段里多了一个 `link` 对象：

```json
"ams": {
  "diag": { ... },
  "link": {
    "rx_bytes": 128640,     // 累计收到的原始字节数
    "rx_frames": 2144,      // CRC 校验通过、完整收下的帧数
    "crc_err": 0,           // CRC8 校验失败的帧数
    "overflow": 0,          // 超长/半截帧被丢弃次数
    "tx_402": 12,           // 0x402 序列号查询的应答次数
    "tx_103": 8,            // 0x103 版本查询的应答次数
    "tx_06": 4,             // 0x06 握手查询的应答次数
    "last_rx_age_ms": 87    // 距离最近一次成功收帧多少毫秒（-1 = 从没收到）
  }
}
```

浏览器直接打开也能看：`http://192.168.2.100/status`（搜 `link`）。

**判读表 —— 一次就能分清 40A3 的真实原因：**

| 现象 | 结论 |
|---|---|
| `rx_bytes` 一直是 **0 / 不涨** | **物理层没数据**：线松、焊点虚、收发器坏、A/B 接反、对端没上电 |
| `rx_bytes` 涨、`crc_err` **猛涨** | **干扰 / 共地不良 / 电源纹波**（电机大电流时最常见） |
| `rx_frames` 正常涨、`tx_402` **一直是 0** | 我们没应答序列号查询（协议分支问题） |
| `tx_402` 在涨、仍报 40A3 | 应答**内容**不对（台号 / 长度 / 型号指纹），查协议内容 |
| `last_rx_age_ms` 一直是 **-1 或很大** | 打印机根本没在跟我们说话 |

### 2. 缓冲送料连续运行超时兜底（30 秒）

v1.1.23 为了让"微动压下了电机不被立刻停掉"，让 `AMCU_motion()` 在
`s_buffer_feed_decision==1` 时不再 `AMCU_drive_stop()`。

副作用：如果微动卡在"一直触发"（常闭接反、线短到 GND、焊接后引脚被拉死），
`decision` 永远是 1，而 `start_trig` 分支每轮都刷新反馈时间戳 →
15 秒的"无反馈超时"**永远不到** → **电机无限转**。

电机长时间空转/堵转的后果不只是发热：大电流让电源纹波变大，
**485 收发器最容易先受影响** —— 表现正好就是打印机报通信异常。

现在加了与"无反馈超时"独立的第二道闸：**同一通道连续送料超过 30 秒强制停**，
并打日志：

```
缓冲送料超时强制停：通道3 连续送料超过 30 秒（微动可能卡在触发态，
检查该路微动是否常闭接反/短接到 GND）
```

### 3. `/diag_reset` 一并清零 485 计数

改完接线后调一次 `POST /diag_reset`，计数从 0 重新算，方便对照前后。

## 二、重要结论：v1.1.23 / v1.1.24 **没有改过 485 协议**

排查过 1.1.22（通信正常）→ 1.1.24 的全部 diff：

| 文件 | 改动 | 是否影响 485 |
|---|---|---|
| `BambuBus.cpp` | 只加了 `last_statu` / `last_statu_ms` 两个字段的赋值 + 3 个只读查询函数 | **否**（协议帧、应答、台号逻辑一行未动） |
| `AMCU.cpp` | 缓冲送料准入放宽 + 让位逻辑 | 间接（会多驱动电机/离合） |
| `filament_sensor.cpp` | 只加 `digitalRead` 只读函数 | 否 |
| `web_server.cpp` | 加 `/sensor_raw`、`/status` 加字段、修 `sensor_set` 解析 | 否 |

所以 40A3 **不是协议层回归**。时间线也指向硬件：

- v1.1.22 刷完 → 通信正常 ✅
- v1.1.23 刷完 → 微动不送料（能进校准流程，说明通信正常）✅
- **用户发现断线 → 焊接**
- v1.1.24 刷完 → 40A3 ❌

中间唯一变化的是**硬件**。

## 三、刷机后请按这个顺序查

### 第 1 步：看 `rx_bytes` 有没有涨

打开 `http://192.168.2.100/status`，连按几次刷新，看 `ams.link.rx_bytes`：

- **完全不涨** → 打印机根本没在跟这块板子说话。查：
  1. 485 的 **A/B 两线有没有接反**（这是最常见的）
  2. 焊接时是否碰松了 485 端子、有没有锡渣搭到相邻脚
  3. 板上 **GPIO14（TX）/ GPIO48（RX）/ GPIO39（DE）** 附近有没有被焊到
  4. 收发器（MAX3485 / SP3485 之类）供电是否正常
- **涨了但 `crc_err` 很大** → 干扰。查共地：微动的 GND 和 485 的 GND 必须是**同一个 GND**，
  但**绝不能把微动的信号线/地线接到 485 的 A 或 B 上**（会把差分线拉死）
- **`rx_frames` 涨、`tx_402` 是 0** → 协议问题，把 `/status` 贴给我

### 第 2 步：观察电机会不会自己一直转

如果一上电（或一进校准）电机就持续转不停，那就是微动卡在触发态。
打开 `http://192.168.2.100/sensor_raw`，看 `raw` 数组：

- 全部 `1`（松开）→ 正常
- 某一路恒 `0`（松开也不回 1）→ **该路微动接的是常闭(NC)端**，要改接常开(NO)端，
  或接线短接到 GND

### 第 3 步：还不行就刷回 v1.1.22 对照

`release/v1.1.22微动没反应/firmware.bin` 是**通信确认正常**的版本。
如果刷回 1.1.22 也报 40A3 → 100% 是硬件，与固件无关。

- `src/BambuBus.cpp` — 485 收发计数（rx_bytes / rx_frames / crc_err / overflow / tx_402 / tx_103 / tx_06 / last_rx_ms）+ 查询接口
